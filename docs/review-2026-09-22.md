# SQLodin implementation review — 2026-09-22

The original implementation did not substantiate its advertised performance or failure-tolerant
multi-master behavior. The changes in this review replace the partial protocol copy with the full
upstream dependency, fix application correctness, reduce bounded payload storage, and make the
verification and benchmark exercise successful work. They do not constitute a production deployment
or proof of optimal CPU/memory use.

## Dependency and consensus

The complete [paxos-odin repository](https://github.com/insanai/paxos-odin) is a Git submodule pinned at
[`a3e1fd78ec8f0429e5024710189ef77fc31961af`](https://github.com/insanai/paxos-odin/commit/a3e1fd78ec8f0429e5024710189ef77fc31961af).
GitHub HEAD and the existing clean sibling checkout agreed on that revision when selected. Builds
import `deps/paxos-odin/src`; they do not depend on that sibling checkout. No upstream source is patched.

[The adapter](../src/paxos.odin) forces `rotating_ownership=true`, stores the no-op for ticks, and delegates
initialization and restoration. Types and transitions are upstream aliases. The complete library is
also available for direct import, including learner/reconfiguration APIs beyond the SQLodin wrapper.

The removed local implementation ignored Prepare/Promise/Nack messages, had no resend path or durable
restore API, unconditionally chose skip slots, and did not defend same-ballot conflicting accepts as
upstream does. The imported implementation supplies bounded recovery, quorum skips, retransmission,
replay and checked memory-floor advancement. Local integration tests cover concurrent owners, absent
owners, lost accepts, and repeated window reuse; the upstream suite exercises the protocol itself.

## Findings and fixes

| Severity | Original issue | Change |
| --- | --- | --- |
| Critical | Text bindings used a freed temporary buffer with `SQLITE_STATIC`. | Borrow immutable mutation storage with explicit byte lengths, then reset/clear bindings before returning. |
| Critical | Deferred COMMIT ran after SQL errors; BEGIN/COMMIT results were ignored. | Checked transactions and rollback on failure; batch application is atomic. |
| Critical | Watermark advanced before successful COMMIT and was lost on reopen. | Persist `_sqlodin_state.applied` in the data transaction, restore on open. |
| High | Partial Paxos omitted recovery/retransmission and bypassed voting for skips. | Import the complete pinned upstream library; remove duplicated protocol files. |
| High | Oversized column names were copied into fixed arrays without bounds checks. | Validate identifiers/lengths and decoded mutation fields before slicing or copying. |
| High | Update was silently ignored; vector values became NULL; deletes and reads ignored step errors. | Execute updates, bind vector BLOBs, reject unknown kinds, and check SQLite results. |
| High | Raw SQL could commit its own transaction or tamper with the watermark. | Authorizer denies transaction/savepoint control, attachment, internal table changes and most PRAGMAs; allow FTS5's read-only `data_version`. |
| High | Snowflake sequence wrapped after 4096 IDs and node IDs were silently masked. | Checked engine generator uses logical milliseconds and rejects out-of-range inputs; restart persistence remains a host contract. |
| High | Benchmark counted failed proposals and never applied SQLite writes. | Route copied packets correctly, consume effects once, check all errors and verify all replicas after timing. |
| High | Simulator treated `SELECT count(*)`'s one result row as the data count. | Compare ordered data digests, validate actual values, and compare every delivered slot with a canonical decision. |
| High | Test/example routing borrowed mutable message payloads and ignored SQL failures. | Shared FIFO harness copies payloads and fails on application/consensus errors. |
| Medium | Every column reserved a full 384-float embedding. | One bounded vector buffer shared across mutation columns. |
| Medium | Repeated DML preparation and per-text allocations wasted CPU. | Eight-entry prepared-statement cache, direct bindings, contiguous application batches. |

SQLite's [binding lifetime contract](https://www.sqlite.org/c3ref/bind_blob.html) requires static buffers
to remain valid through rebinding/finalization. Its [transaction documentation](https://www.sqlite.org/lang_transaction.html)
also makes BEGIN/COMMIT failure handling necessary; an attempted commit is not evidence of success.

## Odin and resource usage

The wrapper uses upstream generic types directly, procedure aliases, explicit errors and caller-owned
state. Internals keep work and caches bounded. `defer` now handles cleanup/rollback rather than unconditional
commit. Source checks enforce the repository's file/procedure/column limits and compiler vet/strict style.
Upstream source inspection found no `new`/`make` allocation calls in consensus source. This does not imply
SQLite, diagnostics, transports or the application are allocation-free.

Measured `size_of` on Darwin arm64 with Odin `dev-2026-09:a2fb372b7`:

| Storage | Original payload | Updated payload |
| --- | ---: | ---: |
| Mutation | 30,840 B | 7,800 B |
| Same upstream node, M=3/W=64/C=16 | 3,026,488 B | 768,568 B |
| Effects, M=3/W=64/C=16 | — | 6,192 B |
| Updated upstream node, M=3/W=256/C=64 | — | 3,026,008 B |

Mutation storage is **74.7% smaller**. The like-for-like node comparison includes the full upstream
recovery state on both sides, so it isolates the payload-layout improvement. It is not a comparison
between the old incomplete node and the new full implementation. The initial shared three-node harness was
2,374,088 bytes before its queue and SQLite allocations; the subsequent shape-cache change reduces
that to 2,351,432 bytes. The simulator caps its lossy network queue at
512 packets; reliable example/test/benchmark routing uses an amortized FIFO instead of shifting every
queued mutation when removing the first packet.

The vector budget is now **384 floats across all columns**, configurable with
`SQLODIN_MAX_MUTATION_VEC_VALUES`, while each vector remains capped at 384 dimensions. This intentional
capacity change trades memory for maximum payload size. Full fixed-capacity mutations are still copied:
a future versioned codec/compact payload design could reduce bandwidth and memory traffic further.

## Initial macOS observations (superseded by the Linux suite)

The previous ~762k writes/sec and fixed ~42ms improvement claims are withdrawn. There is no verified
matched service benchmark, and a local simulation cannot measure a WAN forwarding penalty.

The replacement benchmark runs the same 10,000 structured integer inserts through three SQLite memory
engines in both modes, with three fresh-cluster samples per mode. It includes mutation construction,
packet payload copying, protocol transitions, SQL application on every replica and memory-floor
advancement. Initialization and final verification are outside timing. Single-leader clients submit
directly to the leader; client forwarding is not modeled. Search uses one-row fixtures.

Sockets, codecs, durable consensus journaling/fsync, disk SQLite and WAN latency are excluded. No worker
threads or distributed processes are involved. CPU time and RSS refer to the whole benchmark process,
including both modes and search; they are not per-operation resource measurements.

Two sequential paired observations (10,000 writes per sample, three samples per mode):

| Run / DML cache | Multi-master median ops/s (sample range) | Single-leader median ops/s | Whole-process CPU seconds | Peak RSS |
| --- | ---: | ---: | ---: | ---: |
| 1 / enabled | 30,958 (29,078–32,594) | 33,754 | 2.237 | 7.92 MiB |
| 1 / disabled | 29,054 (28,110–29,357) | 29,300 | 2.445 | 7.91 MiB |
| 2 / disabled | 19,883 (19,499–20,277) | 20,061 | 3.567 | 10.28 MiB |
| 2 / enabled | 24,453 (24,348–27,446) | 33,878 | 2.437 | 10.30 MiB |

The second pair reversed execution order. The cache reduced observed CPU time in both pairs, but
run-to-run variation is substantial. These observations support retaining the bounded cache; they do
not establish a universal speedup. Multi-master did not beat the matched single-leader mode in these
local runs. The first cached process took 5.365 seconds wall time despite 2.237 seconds child CPU time;
whole-process scheduling/startup time is a reason not to equate CPU/wall with steady-state utilization.
The other three process wall times were 2.478, 3.629 and 2.462 seconds, respectively.

The platform is Darwin arm64, Odin `dev-2026-09:a2fb372b7`, system SQLite, release `-o:speed`.
No controlled machine isolation or system-wide resource profile was performed.

Reproduce the matched workloads and cache comparison:

```sh
make deps
odin build bench -o:speed -out:/tmp/sqlodin-bench
odin build bench -o:speed -define:SQLODIN_STATEMENT_CACHE=false -out:/tmp/sqlodin-bench-uncached
python3 tools/measure_bench.py /tmp/sqlodin-bench --iterations=10000
python3 tools/measure_bench.py /tmp/sqlodin-bench-uncached --iterations=10000
```

These runs are not core-pinned or frequency-controlled. Neither a small throughput difference between
ownership modes nor a high CPU/wall ratio establishes distributed superiority or optimal resource use.
All replicas still apply the same ordered write stream through SQLite's single writer.

## Remaining limits and migration notes

1. This repository still needs production transport and certified snapshot transfer. The durable
   host serves retained history and advances its floor after local durable application. The separate
   volatile harness only advances a prefix already applied by every replica.
2. Raw SQL, triggers, functions, collations and schemas must be deterministic and consistent. Ordering
   arbitrary SQL does not make it deterministic. A failed decided mutation stops application; a host
   must define error results/retry handling without silently skipping a chosen operation.
3. Recovery may resubmit an operation in another slot. There is no client request deduplication; raw
   increments and other non-idempotent operations are not exactly-once. A proposal's assigned slot is
   not itself a completed write acknowledgment.
4. Use `durable.next_id` for persisted reservations, including IDs issued for uncommitted proposals.
   The low-level engine generator is process-local and the bit packer remains unchecked. Node
   identities must be uniquely assigned.
5. Each node/effects/SQLite connection requires serialized host access. Watermark reads are local
   read-your-writes checks, not linearizable quorum reads.
6. `Mutation` has changed in-memory layout; do not persist/transmit native struct bytes as a stable
   format. Existing databases without trustworthy application metadata need a coordinated rebuild
   or migration from the matching durable history, not blind replay from slot zero.
7. Consensus functions now return upstream `Consensus_Error`; SQLite functions return SQLodin `Error`.
   `explain_error` supports both. `Node_Options` is upstream's type; tune `election_timeout_ticks` for
   recovery. The private `propose_owned`/local `Skip_Message` shortcut is removed; use `node_propose`
   and upstream transitions. Do not assign `memory_floor` directly.
8. Linux now builds verified SQLite/sqlite-vec sources into local static archives with
   `tools/build_native.py`; macOS retains the platform archive. This review does not validate mixed-endian
   or cross-platform replication.

A durable, multi-process comparison under matched RTTs, failures, payloads, batching and client locality
is still required before claiming faster performance than another distributed database.


## Linux benchmark follow-up

The remote suite runs under `/home/insan/projects/sqlodin` on `agy01` at `10.175.52.19`.
[Raw results and provenance](../benchmarks/results/linux-latest.json) are imported directly by
[the book chapter](book/08_benchmarks.typ). [Reproduction and method](../benchmarks/README.md)
explain timing/resource boundaries and the comparison builds. Linux verification uses the same
34 SQLodin and 79 upstream tests in both profiles and 150,000 modeled fault steps.

This follow-up replaces cache lookup by generated SQL text with a bounded table/column shape key,
and reduces the initial growing FIFO reservation from 256 packets to 32. It compares reference,
shape-cache-only and optimized builds across sequential and twelve-proposal workloads, integer-only
and 256-byte text rows, three-master, single-leader and one-database modes. Seven shuffled rounds
produce 252 individually verified samples; failures are not counted as work. Per-child `wait4`
provides CPU and RSS without carrying over earlier processes' high-water marks.

The review also fixed `sqlite.vec_version` returning storage invalidated by statement finalization:
it now returns an allocator-owned string which callers delete. Extension-registration error strings
are freed with SQLite's allocator. These changes are included in the measured source manifest.

The book no longer presents the earlier proof sketches as mechanical verification, unrestricted
Snowflake uniqueness, nonexistent API signatures, constant CPU instruction timings or guaranteed
local-read latencies. It distinguishes slot choice from client completion and describes the
required history, durability, determinism and retry contracts.

Final Linux medians with 256-byte text rows: multi-master **68,350
writes/s** sequentially and **95,752 writes/s** with twelve proposals in
flight. Relative to the reference build, those are **7.3%**
and **10.5%** increases on this host.
Sequential peak RSS fell from **29.95 MiB** to
**28.16 MiB**. CPU utilization was approximately one full pinned
core; this is not evidence of multi-core scaling. Matched single-leader results and all sample ranges
are in the JSON and book, and the sequential modes are essentially tied in this workload.

The historical source manifest was checked against the then-current local tree after retrieval. The
[Linux verification log](../benchmarks/results/linux-verification.log) records the passing checks.
The downloaded official SQLite/sqlite-vec releases were independently checked against all five
source/header hashes used by the builder after measurements completed.


## Durability-first follow-up

The follow-up adds `src/durable`, a fixed-membership host with one on-disk SQLite database holding
both application data and an explicit Paxos journal. Promise/vote/decision records and a SHA-256
chain head commit before the enforced effects gate opens. Restart validates identity, history and
application-prefix evidence, restores the upstream ledger and completes any unapplied decision suffix.
The codec stores logical little-endian values, not Odin struct padding or borrowed pointers.
Write/apply/allocation failures poison the host. Outgoing packets own their payloads; old range
requests use retained disk decisions, so advancing the memory floor does not silently lose history.

New regressions cover journal/application boundaries, actual SIGKILL at acknowledgement, all-voter
restart, disk-full/read-only failures, corruption, identity/locking, durable promises/votes, concurrent
master proposals and history beyond the memory window. ID blocks are reserved durably across restart
and wall-clock rollback. SQL authorization now covers triggers reached through structured DML and
rejects read-API PRAGMAs that could disable durability. Inactive NaN fields are rejected explicitly
because every logical payload field participates in protocol value identity.

Linux SQLite is updated from 3.50.4 to 3.51.3, including the upstream WAL-reset corruption fix. Source
SHA-256 and the release-page SHA3-256 are checked. The older memory benchmark retains its original
3.50.4 metadata and source manifest; its performance numbers do not describe this new durable host.

The durable host is not a completed production server. It requires serialized access, deterministic
SQL/schema/functions, unique replica identities, correct transport and ticks, and request-level
idempotency/deduplication. It retains complete history: disk space and restart work grow with history.
Snapshot compaction, membership changes, lost-disk replacement, distributed read fencing and safe
backup rollback/rejoin remain outside this implementation. SIGKILL and injected failures are scoped
evidence, not certification against power failure or a filesystem that fails to honor sync.

The new supported-workload benchmark records official comparison-server release binaries and the stock
cowsql demo, with disk persistence paths clearly separated. SQLodin's embedded measurements cannot
be ranked as equivalent to authenticated network servers with linearizable reads. JSON results,
source/binary hashes and resource boundaries are imported by the book's durable-workload chapter.

The final durable-host suite contains 43 SQLodin tests and 79 pinned upstream tests, run in both
profiles on Linux. The result logs and process-crash JSON retain the verification evidence.
